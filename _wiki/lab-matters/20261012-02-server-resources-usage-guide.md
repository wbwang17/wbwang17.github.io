# 组内事项：服务器与 AiStation 算力平台使用指南

发布时间：2026-10-12

本文介绍目前常用的两类计算资源：组内 L20 服务器和大组 AiStation 算力平台。请先了解存储目录、账号权限和资源释放规则，再开始上传数据或运行实验。

> 为避免泄露内部网络和账号信息，本文不公开登录地址、端口、账号或密码。首次使用前，请向服务器管理员获取当前有效的登录入口和个人凭据。文中截图已进行脱敏处理，实际界面可能随平台升级有所变化。

## 1. 基本安全要求

1. 账号只限本人使用，不得转发登录地址、账号、密码、SSH 私钥或临时连接信息。
2. 不要把密码写入代码、配置文件、Shell 脚本、实验日志或公开 Git 仓库；截图发到群里或写入文档前也要检查敏感信息。
3. 不要使用与个人邮箱、校园系统等其他服务相同的密码。平台生成的临时密码仅用于对应环境。
4. 不得查看、复制、修改或删除其他用户的私人文件。确需使用共享数据时，应先确认数据来源、授权范围和共享位置。
5. 未公开论文、受限数据集、审稿材料和个人信息不得上传到未经确认的平台或第三方服务。

## 2. L20 组内服务器

L20 服务器适合长期维护代码环境、保存组内项目和运行常规训练任务，通过 SSH 远程登录。

### 2.1 资源概述

- 3 块 NVIDIA L20 GPU，每块 48 GB 显存；
- 2 颗 Intel Xeon Silver 4410Y 处理器；
- 4 根 32 GB DDR5 ECC REG 内存；
- 1 块 480 GB SATA SSD，作为系统盘；
- 4 块 1.92 TB SATA SSD，主要用于 `/home`；
- 1 块 10 TB HDD，主要用于 `/data`。

硬盘的实际可用容量、挂载方式和剩余空间以服务器当前状态为准。开始大规模实验前，可以使用 `df -h` 检查磁盘空间，使用 `nvidia-smi` 查看 GPU 占用情况。

### 2.2 账号与目录

首次使用时，请联系组内服务器管理员创建个人账号，并分配个人目录：

- `/home/<username>`：个人启动目录。主要保存项目代码、Conda 环境、配置文件和体积较小的实验记录；
- `/data/<username>`：个人数据目录。主要保存数据集、模型权重、缓存和其他大文件。

`/home` 空间有限，不要长期存放数据集、训练权重、压缩包或大量日志。大文件应放在个人 `/data` 目录，并在代码中通过配置文件或软链接引用。不要把所有内容直接堆在目录根部，建议按项目组织：

```text
/data/<username>/
├── datasets/
├── checkpoints/
├── pretrained/
└── projects/
```

部分目录可能对其他用户可读，这是为了方便共享数据，不代表可以随意修改。**未经确认，不得删除、移动或覆盖其他用户目录中的任何文件。**

### 2.3 软件与环境

每个项目应建立独立的 Conda 环境，并记录关键依赖版本。不要为了单个项目反复修改系统 CUDA、驱动或全局 Python 环境。

如需安装新的 CUDA 版本、系统库或其他需要管理员权限的软件，请先完成以下检查：

1. 查看 `/usr/local/` 中是否已经存在可用版本；
2. 确认 Conda、容器或项目本地安装是否可以解决；
3. 说明软件用途、版本要求和可能影响，再联系服务器管理员处理。

## 3. AiStation 大组算力平台

AiStation 是大组共享的算力管理平台，使用方式类似内部算力租赁平台。目前主要提供 10 块 NVIDIA GeForce RTX 3090 GPU，每块 24 GB 显存。

平台资源遵循先申请、先使用的原则。开发环境创建后会独占所选资源，因此完成实验后必须先保存需要保留的环境，再及时删除开发环境、释放 GPU。禁止创建环境后长期空闲占用。

### 3.1 登录与个人工作目录

平台登录入口和凭据请向管理员（组内高年级正在使用的同学）获取，不在公开页面记录。首次登录后，先在“数据管理 - 文件管理”中创建个人工作目录，建议使用能够明确区分本人的名称，例如 `<username>_workspace`。

![在文件管理中创建个人工作目录]({{ '/assets/images/wiki/server-resources/01-create-workspace.png' | relative_url }})

个人目录用于保存代码、数据和需要跨环境保留的文件。开发环境本身可能被删除，因此不要把唯一副本只放在容器临时目录中。

### 3.2 创建开发环境

进入“业务管理 - 开发环境”，创建新的开发环境。创建时重点确认：

1. 环境名称包含本人标识和任务简称，便于后续管理；
2. 选择合适的基础镜像或本人之前保存的镜像；
3. 根据任务需要选择 CPU 和 GPU 数量，不要超额申请；
4. 选择当前空闲节点；
5. 挂载需要使用的个人工作目录。

![创建开发环境并选择镜像与计算资源]({{ '/assets/images/wiki/server-resources/02-create-environment.png' | relative_url }})

创建完成后先确认环境状态为“运行中”，再进行远程连接。若实验只需要单卡，请不要一次申请多卡；显存不足时，应先排查 batch size、输入尺寸、梯度累积和无用进程，再考虑增加资源。

### 3.3 获取 SSH 信息并连接

在开发环境列表中查看 SSH 信息，平台会给出当前环境对应的连接命令和临时密码。连接地址、端口和密码可能随环境变化，不要把旧信息写死在公开文档中。

![从开发环境列表获取 SSH 连接信息]({{ '/assets/images/wiki/server-resources/03-get-ssh-details.png' | relative_url }})

可以在本地终端、VS Code Remote SSH、PyCharm 或其他 SSH 客户端中连接。首次连接时应核对主机信息；如果出现异常的主机指纹变更、连续认证失败或无法解释的跳转，不要反复尝试，先联系管理员确认。

### 3.4 上传文件并开始开发

代码和数据可以通过平台文件管理、SFTP 或 `scp` 上传。大规模项目优先使用 Git 管理代码，数据集和模型权重放入个人工作目录，不要把大文件提交到 Git 仓库。

![通过文件管理上传文件]({{ '/assets/images/wiki/server-resources/04-upload-files.png' | relative_url }})

开始实验前建议依次检查：

```bash
nvidia-smi
df -h
pwd
```

同时记录基础镜像、Python、PyTorch、CUDA、关键依赖、数据路径和启动命令。不要只依赖终端历史记录，否则环境迁移后很难复现实验。

### 3.5 保存环境镜像

需要保留当前软件环境时，在开发环境详情页选择“保存镜像”。镜像名称应包含本人标识、项目简称和版本号，备注中写明主要框架版本及用途。

![将开发环境保存为个人镜像]({{ '/assets/images/wiki/server-resources/05-save-image.png' | relative_url }})

保存操作不是完成备份的唯一证据。提交保存后，应检查任务日志和镜像管理页面，确认镜像状态正常，再删除原开发环境。项目代码、实验结果和重要数据仍应单独保存到持久化目录或版本库。

### 3.6 删除开发环境并释放资源

确认镜像和文件已经保存后，及时删除不再使用的开发环境。删除开发环境前再次检查：

- 重要代码是否已经提交或同步；
- 实验结果和权重是否位于持久化目录；
- 需要复用的环境是否已成功保存为镜像；
- 当前是否仍有训练、下载或数据处理任务运行。

![确认保存后删除开发环境]({{ '/assets/images/wiki/server-resources/06-delete-environment.png' | relative_url }})

停止终端或关闭浏览器不会自动释放 GPU，必须在平台中删除或停止对应环境。发现长期无人使用的环境时，不要自行删除他人资源，应联系管理员处理。

### 3.7 任务管理

对于命令明确、无需交互调试的训练或推理任务，可以使用“任务管理”创建任务。配置时确认镜像、启动命令、数据挂载、资源数量和节点选择，避免使用仍在频繁修改的临时代码。

![创建非交互式训练任务]({{ '/assets/images/wiki/server-resources/07-task-management.png' | relative_url }})

任务启动后应检查日志是否正常输出，并记录任务名称、代码版本、配置文件和结果目录。任务结束后同样需要确认资源已经释放。

## 4. 公共资源使用规范

### 4.1 GPU 使用

- 开始任务前检查 GPU 使用率、显存和现有进程，不要抢占正在使用的设备；
- 训练脚本应明确指定 GPU，不要默认占用所有可见设备；
- 调试阶段先使用小数据、小 batch size 和较短运行时间；
- 程序异常退出后检查是否仍有残留进程；
- 不得终止其他用户的进程，发现异常占用时联系本人或管理员。

### 4.2 文件与磁盘

- 定期删除无用 checkpoint、重复数据、解压后的临时包和过期日志；
- 大文件下载前先确认磁盘剩余空间和现有共享副本；
- 数据集尽量只保留一份可靠副本，通过只读共享或软链接复用；
- 重要代码必须使用 Git 或其他版本管理方式，服务器不是唯一备份；
- 删除大量文件前再次检查路径，避免在变量为空或目录错误时执行递归删除命令。

### 4.3 问题反馈

向管理员反馈问题时，请提供以下信息，但不要在公开渠道粘贴密码、私钥或完整凭据：

1. 使用的平台和环境名称；
2. 问题发生时间；
3. 执行的命令或操作步骤；
4. 完整报错文本或经过脱敏的截图；
5. 已经尝试过的排查方法；
6. 是否影响其他正在运行的任务。

清楚的问题描述通常比“服务器不能用”“环境有问题”更容易得到有效帮助。

## 5. 使用前检查清单

- 已从管理员处获得个人账号和当前有效的登录方式；
- 已了解 `/home`、`/data` 或平台持久化目录的用途；
- 已确认代码、数据、权重和日志分别保存在哪里；
- 已建立独立环境并记录关键依赖版本；
- 已检查 GPU 和磁盘资源；
- 已确认任务不会覆盖或删除他人文件；
- 已规划实验完成后的结果保存、镜像保存和资源释放步骤。

服务器是组内共享的科研基础设施。正确使用不仅是把代码运行起来，还包括保护凭据、尊重他人目录、控制资源占用、保留可复现实验记录，并在任务结束后及时清理和释放资源。
